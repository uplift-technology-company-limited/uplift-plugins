# page — เอกสารใน Plane ที่คนอ่านรู้เรื่อง

ต่อยอดจากหลักของ `management-talk`: คนอ่านรู้จักชื่อระบบ ชื่อโมดูล เลขงาน `PROJ-12` เลข PR แต่ไม่ได้อ่านโค้ด
เขาเปิด page เพื่อรู้ว่า **ของนี้คืออะไร ทำไปถึงไหน ต้องตัดสินใจอะไร** ส่วนวิธีทำเป็นของ developer ที่จะเลื่อนลงไปอ่านเอง

page ที่อ่านไม่รู้เรื่องมักเกิดจากการเอาเอกสารที่เขียนให้ AI หรือให้ developer อ่าน ไปวางตรง ๆ
ประโยคที่ต่อด้วยลูกศรกับขีดยาวเป็นทอด ๆ อ่านเร็วสำหรับคนเขียน แต่คนอ่านต้องถอดรหัสเองว่าอะไรเป็นเหตุ อะไรเป็นผล

## 1. ก่อนเขียน: ตอบให้ได้ 3 ข้อ

1. **ใครอ่าน** — ทีมภายใน / PM / lead / ลูกค้า (ถ้าลูกค้าอ่าน ห้ามมีชื่อคน ความลับ หรือตัวเลขภายใน)
2. **อ่านแล้วต้องได้อะไร** — เข้าใจภาพรวม / รู้สถานะ / ตัดสินใจ / ใช้เป็นแบบอ้างอิงตอนทำงาน
3. **ของต้นทางคืออะไร และเป็นสถานะไหน** — ออกแบบไว้ / กำลังทำ / ใช้งานจริงแล้ว — ต้องบอกบนสุดของ page เสมอ คนอ่านจะได้ไม่เข้าใจผิดว่าแบบที่ยังไม่ทำคือของที่ใช้งานได้

**อย่านำขึ้นถ้าไม่ได้ถูกขอ:** สัญญา / TOR / ใบเสนอราคา / อะไรจาก `_secrets/` · ถ้าไม่แน่ใจว่าเอกสารไหนควรขึ้น ให้ถามก่อน (เคยมีคนนำ TOR ขึ้น page แบบ public โดยไม่มีใครสั่ง แล้วต้องตามลบ)

```
# ชื่อเรื่อง (ภาษาคน)

## สรุป
3-5 บรรทัด อ่านจบแล้วรู้ว่าเรื่องนี้คืออะไร ทำไปถึงไหน มีอะไรต้องตัดสินใจ

## <หัวข้อที่ 1 — ภาษาคน บอกผลลัพธ์>
ย่อหน้าหรือ bullet สั้น ๆ ภาษาคน

รายละเอียดเทคนิค
- ชื่อตาราง / endpoint / ไฟล์ / flag อยู่ตรงนี้

## <หัวข้อที่ 2> ...

## ต้องตัดสินใจ / ยังไม่ชัด   (ถ้ามี)
```

**หัวข้อ** เขียนเป็นสิ่งที่ผู้ใช้ได้หรือสิ่งที่ระบบทำ ไม่ใช่ชื่อโค้ด

| แย่ | ดี |
|---|---|
| `notifyService` dispatcher + fan-out | แจ้งเตือนทุกช่องทางออกจากจุดเดียว |
| Wave 1 — Workflow data model (ข้อ 8, 9, 10) + engine | สายอนุมัติ: เก็บข้อมูลยังไง และเรื่องเดินตามขั้นยังไง |
| ADR-003: SSE over WS | ทำไมเลือก SSE แทน WebSocket |

**รายละเอียดเทคนิค** ใส่ได้เต็มที่ แต่อยู่ใต้หัวข้อย่อย "รายละเอียดเทคนิค" หรือในตาราง ไม่ปนในประโยคสรุป

## 3. กติกาการเขียน (ส่วนที่ page ส่วนใหญ่พลาด)

### ลูกศร → และขีดยาว —

ทั้งสองตัวแทนคำเชื่อมที่คนอ่านต้องเดาเอง ให้เขียนคำนั้นออกมา

| เขียนแบบนี้ | แทน |
|---|---|
| `A → B` (เป็นเหตุผล) | "A ทำให้ B" / "เมื่อ A แล้วจึง B" |
| `A → B → C` (เป็นขั้นตอน) | รายการลำดับเลข 1. 2. 3. |
| `X — Y` (อธิบายเพิ่ม) | "X คือ Y" / ขึ้นประโยคใหม่ / วงเล็บ |
| `A · B · C` ยาวเกิน 3 ชิ้น | bullet หรือตาราง |

ลูกศรใช้ได้ที่เดียว: ในแผนภาพหรือตารางที่คอลัมน์หนึ่งคือ "จาก" อีกคอลัมน์คือ "ไป" · ขีดยาวไม่ต้องใช้เลย
ตรวจก่อนนำขึ้นด้วย `scripts/check.sh <ไฟล์.md>` (นับ → — · `[[...]]` และบรรทัดยาวเกิน)

### แผนภาพ

Plane ไม่วาด mermaid เอง ถ้าวางโค้ดไว้จะขึ้นเป็นกล่องโค้ดอ่านไม่ออก แต่ **`publish.py` render บล็อก ```` ```mermaid ```` เป็นรูป PNG แล้วแนบเข้า page ให้เอง** (ใช้ `scripts/render_mermaid.mjs` ฟอนต์ไทย Noto Sans Thai) รูปในเครื่องแบบ `![](path.png)` ก็แนบให้เหมือนกัน

- ข้อความรอบรูปต้องอ่านรู้เรื่องโดยไม่ต้องดูรูป รูปช่วยให้เห็นภาพ ไม่ใช่ที่เดียวที่มีข้อมูล
- ขั้นตอนสั้น ๆ ใช้รายการลำดับเลขก็พอ ไม่ต้องมีรูปทุกเรื่อง

### ลิงก์และการอ้างถึงเอกสารอื่น

คนอ่าน page เปิด KB/Obsidian หรือ repo ไม่ได้ และ Plane ไม่รู้จัก `[[ลิงก์ Obsidian]]` มันขึ้นเป็นวงเล็บเหลี่ยมดิบ คนอ่านไม่รู้ว่าหมายถึงอะไร

- อ้างเอกสารใน KB: เขียนชื่อเต็มพร้อมบอกว่าอยู่ที่ไหน เช่น "รายการงาน Phase 2 (ไฟล์ phase2-tasklist ใน KB)"
- อ้างอีก page ใน Plane: ใส่ลิงก์จริง `[ชื่อ page](https://plane.uplifttech.dev/...)`
- อ้างไฟล์ในโค้ด: บอก repo + branch + path ครั้งเดียวในบรรทัดที่มา ไม่ต้องซ้ำทุกย่อหน้า
- คำที่คนในทีมพูดกันเอง ("tasklist", "Wave 2", "ข้อ 8") ต้องบอกว่าหมายถึงเอกสารไหนตอนที่พูดถึงครั้งแรก

### ภาษา

- ไทยเป็นหลัก คำเทคนิคที่ทีมใช้กันอยู่แล้ว (API, schema, migration, branch, UAT) คงไว้ ไม่ต้องแปล
- ประโยคมีประธานและกริยา "ระบบสร้าง PDF ให้อัตโนมัติ" ไม่ใช่ "auto gen PDF"
- ไม่ใช้ตัวหนาทุกบรรทัด ตัวหนามีไว้ให้สายตาหยุด ถ้าหนาทุกที่ก็ไม่มีที่ให้หยุด
- ตัวเลขและวันที่เขียนเต็ม "22 ต.ค. 2569" ไม่ใช่ "W9.5"
- คงไว้เสมอ: เลขงาน Plane, เลข PR, ชื่อโมดูล/ระบบ · ตัดออกจากส่วนสรุป: ชื่อฟังก์ชัน, path ไฟล์, SHA

### ตัวอย่าง

ต้นทาง (เขียนให้ developer):
> `notifyService(target, payload)` → resolve target → userId[] (role/site/company) — dedupe · broadcast ใหญ่เข้า BullMQ batch → fan-out ต่อ channel (WEB → DB row + Redis publish → SSE)

แบบ page:
> **แจ้งเตือนทุกช่องทางออกจากจุดเดียว**
>
> ทุกโมดูลส่งแจ้งเตือนผ่านตัวกลางตัวเดียว ผู้ส่งเลือกได้ว่าจะส่งถึงใคร: รายคน ทั้ง role ทั้งไซต์ หรือทั้งบริษัท ระบบตัดคนที่ซ้ำให้ แล้วส่งตามช่องทางที่แต่ละคนเปิดไว้ (เว็บ LINE SMS อีเมล) ถ้าเป็นแจ้งเตือนในเว็บ กระดิ่งจะเด้งทันทีโดยไม่ต้องรีเฟรช
>
> รายละเอียดเทคนิค
> - `notifyService(target, payload)` ใน `notification/v1/services/`
> - realtime: Redis pub/sub แล้วส่งออกทาง SSE `GET /notifications/stream`
> - ส่งทีละมาก ๆ เข้าคิว BullMQ

## 4. นำขึ้น / อัปเดต page

`<skill>` คือโฟลเดอร์ของ skill นี้ (ติดตั้งแบบ user คือ `~/.claude/skills/page` ติดตั้งผ่าน plugin ใช้ path ที่ plugin วางไว้) · `<project>` คือ identifier หรือชื่อโปรเจกต์ใน Plane

Plane public API (`/api/v1/...`) **สร้างหรือแก้ page ไม่ได้** ต้องทำผ่าน Django shell ในคอนเทนเนอร์ API ของ Plane (ค่าเริ่มต้น `uplift-dev-plane-api-1` เปลี่ยนได้ด้วย env `PLANE_API_CONTAINER`) จึงต้องรันบนเครื่องที่ Plane ตั้งอยู่ ใช้ script ที่เตรียมไว้

**ถ้ารันที่อื่น** (claude.ai, เครื่องที่ไม่มี docker ของ Plane) script นำขึ้นใช้ไม่ได้ ให้ทำส่วนเขียน (ข้อ 1-3) ให้ครบ แล้วส่งไฟล์ markdown ให้ผู้ใช้วางเองใน Plane · แผนภาพ mermaid ให้บอกผู้ใช้ว่าต้อง render เป็นรูปก่อนแปะ (Plane ไม่วาด mermaid)

```bash
# ตรวจการเขียนก่อน
<skill>/scripts/check.sh page.md

# สร้างใหม่ (สิทธิ์และเจ้าของก๊อปจาก page อ้างอิงในโปรเจกต์เดียวกัน)
python3 <skill>/scripts/publish.py page.md --project <project> --name "ชื่อ page"

# อัปเดต page เดิม (เก็บ id เดิม) — ใช้ได้เฉพาะ page ที่ยังไม่มีใครเปิด ดูคำเตือนข้างล่าง
python3 <skill>/scripts/publish.py page.md --page-id <uuid>

# ดูรายการ page ในโปรเจกต์
python3 <skill>/scripts/publish.py --list --project <project>
```

- **คำเตือน: อัปเดตทับ page ที่เคยมีคนเปิดแล้ว เนื้อหาเก่าจะกลับมา** Plane เก็บเนื้อหาจริงเป็นเอกสาร Yjs ในเซิร์ฟเวอร์ live และในเบราว์เซอร์ที่เคยเปิด page นั้น พอเราเขียน HTML ใหม่ลงฐานข้อมูล ตัวที่ค้างอยู่จะบันทึกของเก่าทับกลับภายในไม่กี่นาที (เจอจริง 19 ก.ย. 2569: เขียนทับตอน 09:28 แล้วถูกทับกลับตอน 09:30)
  - page ที่มีคนเปิดแล้ว ให้ **สร้าง page ใหม่ แล้ว archive ตัวเก่า** และ archive ก็ต่อเมื่อ publish.py พิมพ์ "สร้างแล้ว <id>" จริงเท่านั้น (อย่าต่อคำสั่ง archive หลัง `publish.py | tail` ด้วย `&&` เพราะ exit code ของ pipe มาจาก tail ทำให้ archive ทำงานแม้ publish ล้ม) (`page.archived_at = timezone.now()` ซึ่งกู้คืนได้) แล้วส่งลิงก์ใหม่ให้ผู้ใช้
  - หลังนำขึ้น รอ 2-3 นาทีแล้วอ่าน `description_html` ซ้ำ ถ้า `updated_at` เปลี่ยนหรือเนื้อหาเก่ากลับมา แปลว่าโดนทับ
- script แปลง markdown เป็น HTML (markdown-it) แล้วเขียนเข้า `Page.description_html` และล้าง `description_binary` ตอนอัปเดต เพื่อให้ editor โหลดเนื้อหาใหม่จาก HTML
- ลบ page: ใช้ soft delete (`page.delete()`) กู้คืนได้ · ลบเฉพาะที่ผู้ใช้สั่ง
- **เขียนลงฐานข้อมูลได้ไม่ได้แปลว่าคนอ่านเห็นถูก** หลังนำขึ้นต้องตรวจเองก่อนบอกว่าเสร็จ
  1. HTML ใน `Page.description_html` ไม่มี `[[` ไม่มี `language-mermaid` และจำนวน `<image-component` ตรงกับจำนวนรูป
  2. รูปทุกรูปโหลดได้จริง: เรียก `/api/assets/v2/workspaces/<slug>/projects/<project>/<asset>/` (Django test client + `force_login`) ได้ 302 แล้ว curl URL ปลายทางได้ 200 `image/png`
  3. บอกผู้ใช้ให้เปิด page จากเว็บ 1 ครั้งเพื่อยืนยันหน้าตา ถ้าหน้าว่างหรือจัดหน้าเพี้ยน ให้แก้
