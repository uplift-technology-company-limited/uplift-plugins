# plane-plan: แผนแก้งานจากใบ Plane ที่ตรงกับความจริง

แผนที่เขียนจากเนื้อหาใบอย่างเดียวจะล้าสมัยตั้งแต่วันแรก เพราะใบบอกสภาพตอนที่มีคนเปิดใบ ไม่ใช่สภาพตอนนี้
แผนชุดที่เป็นที่มาของ skill นี้อ้างใบ 52 ใบ และเขียนเหมือนทุกข้อยังพัง ทั้งที่โค้ดแก้ไปแล้ว 19 ใบ และแก้บางส่วนอีก 25 ใบ
ถ้าเอาแผนนั้นไปแตกงาน ทีมจะทำซ้ำของที่เสร็จแล้วราวสองในสาม

skill นี้ใช้คู่กับ skill `page` ในปลั๊กอินเดียวกัน กติกาการเขียนและขั้นตอนนำขึ้น Plane ให้ทำตาม `page` ทุกข้อ
skill นี้กำหนดเพิ่มสามอย่าง คือ ต้องตรวจอะไรก่อนเขียน แผนต้องมีหัวข้ออะไร และตารางใบต้องหน้าตาแบบไหน

## 1. ตรวจสถานะจริงก่อนเขียนแผน

ห้ามข้ามขั้นนี้ และห้ามเขียนแผนก่อนทำขั้นนี้จบ

1. **รวบรวมรายการใบ** ที่แผนจะครอบคลุม พร้อมสถานะปัจจุบันบน Plane
2. **อ่านคอมเมนต์ของทุกใบ** โดยเฉพาะคอมเมนต์ล่าสุด มักมีบันทึกว่าแก้แล้วเมื่อไหร่ ตรวจบน tier ไหนแล้ว ผ่านหรือไม่ผ่านตรงไหน และอะไรรอการตัดสินใจ
3. **เทียบกับโค้ดบน branch ที่ deploy อยู่** (ปกติคือ `dev`) อ่านจาก remote ref หรือ worktree ที่สร้างจาก remote ไม่ใช่ checkout ในเครื่องที่อาจค้างอยู่ branch เก่า บันทึก commit ที่ใช้เทียบไว้
4. **ตัดสินทีละใบ** เป็นหนึ่งในสี่แบบ
   - แก้แล้วในโค้ด
   - แก้บางส่วน (ระบุว่าเหลืออะไร)
   - ยังไม่แก้
   - บอกจากโค้ดไม่ได้ (ระบุว่าต้องใช้อะไรจึงจะบอกได้ เช่น ข้อมูลบน dev หรือการลองจริง)
5. **จดสิ่งที่ยืนยันไม่ได้** ให้ชัด การอ่านโค้ดบอกได้ว่ามีโค้ดที่แก้เรื่องนั้นอยู่ ไม่ได้บอกว่ามันทำงานบนหน้าจอ

ถ้าใบมีมาก ให้แบ่งเป็นกลุ่มตามเรื่อง แล้วส่ง subagent อ่านโค้ดคู่ขนานกันได้ กำชับว่าเป็นงานอ่านอย่างเดียว ต้องอ้างไฟล์และบรรทัดทุกข้อสรุป และต้องบอกสิ่งที่ไม่ได้ตรวจ
ข้อค้นพบที่หนัก (เช่น ช่องโหว่ด้านสิทธิ์) ให้เปิดโค้ดยืนยันเองก่อนใส่ในแผน

## 2. จัดทุกใบลงหนึ่งในสี่กลุ่ม

หนึ่งใบอยู่ในกลุ่มเดียว ถ้าใบมีงานหลายประเภท ให้จัดตามงานที่ใหญ่กว่า

| กลุ่ม | ใบแบบไหน | ใครลงมือ |
|---|---|---|
| งานที่ต้องเขียนโค้ด | ยังไม่แก้ หรือแก้บางส่วนและส่วนที่เหลือเป็นโค้ด | ทีม dev |
| งานที่ไม่ใช่โค้ด | แก้ได้ด้วยการแก้ข้อมูล แก้เนื้อหา หรือตั้งค่าในระบบ | ผู้ดูแลระบบหรือเจ้าของข้อมูล |
| เรื่องที่รอการตัดสินใจ | เริ่มไม่ได้จนกว่าจะมีคนเลือกทาง | เจ้าของผลิตภัณฑ์ |
| ใบที่ต้องตรวจซ้ำ | โค้ดแก้แล้วแต่ยังไม่มีใครเห็นบนหน้าจอ หรือบอกจากโค้ดไม่ได้ | QA |

เรื่องที่เจอใหม่ระหว่างตรวจและไม่อยู่ในรายการใบเดิม ไม่จัดเข้ากลุ่มไหน ให้แยกเป็นหัวข้อของตัวเองและเปิดใบแยก

## 3. หัวข้อของแผน

ใช้หัวข้อชุดนี้ตามลำดับนี้ **ชื่อหัวข้อเป็นภาษาอังกฤษ เนื้อหาเป็นภาษาไทย** (Anon กำหนด 13 ต.ค. 2569) ใส่เลขนำหน้าหัวข้อเพื่อให้อ้างถึงกันได้ ชื่อ page ขึ้นต้นด้วยเรื่อง ไม่ใช่วันที่

| # | หัวข้อ | เนื้อหา |
|---|---|---|
| 1 | Executive Summary | สรุปสำหรับผู้บริหาร |
| 2 | Current Status | สถานะปัจจุบันของทุกใบ |
| 3 | Code Work | งานที่ต้องเขียนโค้ด |
| 4 | Non-code Work | งานที่ไม่ใช่โค้ด |
| 5 | Decisions Needed | เรื่องที่รอการตัดสินใจ |
| 6 | Re-verify on Dev | ใบที่ต้องตรวจซ้ำ (เปลี่ยนชื่อ tier ตามที่ตรวจจริง) |
| 7 | New Findings | เรื่องใหม่ที่เจอระหว่างตรวจ |
| 8 | How We Close | วิธีปิดงาน |
| 9 | References | อ้างอิง |

### 1. Executive Summary

เขียนตามหลัก `management-talk`: คนอ่านรู้จักชื่อระบบและเลขใบ แต่ไม่ได้อ่านโค้ด อ่านหัวข้อนี้จบต้องตัดสินใจได้

- บรรทัดแรกเป็นสถานะหนึ่งบรรทัด ตัวหนา มีตัวเลข เช่น "เสร็จในโค้ดแล้ว 19 จาก 52 ใบ อีก 33 ใบยังมีงานค้าง ซึ่งมีเพียง 19 ใบที่ต้องเขียนโค้ดเพิ่ม"
- **ผลต่อผู้ใช้ตอนนี้** เป็นเรื่องที่ผู้ใช้เห็น ไม่ใช่ชื่อโมดูล และบอกหนึ่งบรรทัดว่าตัวเลขยืนยันด้วยวิธีใด
- **งานที่เหลือแบ่งตามคนที่ต้องลงมือ** เป็นตารางประเภท จำนวน ใครลงมือ ถ้าไม่รู้ชื่อคนให้ใส่บทบาท ห้ามเดาชื่อ
- **เรื่องใหม่ที่ต้องรู้** เฉพาะเรื่องที่หนักพอให้ผู้บริหารต้องรู้
- **ขั้นถัดไป** เป็นรายการลำดับเลข อ้างเลขหัวข้อในแผน

เก็บเลขใบไว้ ตัดชื่อไฟล์ ชื่อฟังก์ชัน และ commit ออก ไม่ใช้คำกั๊กเช่น "น่าจะ" กับเรื่องที่ยืนยันแล้ว และไม่ยกข้อสันนิษฐานขึ้นเป็นข้อเท็จจริง

### 2. Current Status

บอกตัวเลขรวมสี่แบบจากข้อ 1 แล้วตามด้วยตารางเดียว คือใบที่สถานะบน Plane ไม่ตรงกับโค้ด
ทั้งสองทิศ คือ Todo ทั้งที่โค้ดแก้แล้ว และ Rework ทั้งที่ติดแค่ไม่มีข้อมูลทดสอบหรือมีโค้ดใหม่หลังการตรวจครั้งล่าสุด
ไม่ต้องไล่ทุกใบซ้ำที่นี่ เพราะทุกใบอยู่ในหัวข้อ 3 ถึง 6 อยู่แล้ว

### 3 ถึง 6. Code Work, Non-code Work, Decisions Needed, Re-verify on Dev

แต่ละหัวข้อขึ้นต้นด้วยจำนวนใบหนึ่งบรรทัด แล้วเป็นตารางตามข้อ 4 ช่อง "สรุปเนื้อหา" ของแต่ละหัวข้อเขียนต่างกัน

| หัวข้อ | ช่องสรุปเนื้อหาบอกอะไร | เรียงตาม |
|---|---|---|
| Code Work | สิ่งที่ยังเหลือต้องทำ ในมุมที่ผู้ใช้เจอ | ผลต่อผู้ใช้ จากหนักไปเบา |
| Non-code Work | ปัญหา และต้องไปแก้ที่หน้าไหนของระบบ | คนที่ลงมือ |
| Decisions Needed | คำถามที่ต้องตอบ เขียนเป็นคำถามที่ตอบได้ | งานที่ติดอยู่ข้างหลัง |
| Re-verify on Dev | สิ่งที่ต้องเห็นบนหน้าจอ และข้อมูลทดสอบที่ต้องเตรียมก่อน | ลำดับที่เดินตรวจสะดวก |

### 7. New Findings

ตารางรูปแบบเดียวกัน ถ้ายังไม่มีใบ ช่องรหัสเขียน "ยังไม่มีใบ" และช่องสถานะเขียน "ยังไม่เปิดใบ"
ท้ายสรุปเนื้อหาของแต่ละแถวต้องบอกในวงเล็บว่า ยืนยันจากโค้ดแล้ว หรือ ยังไม่ได้ยืนยัน

### 8. How We Close

สามส่วน คือ ลำดับการทำ (รายการลำดับเลข อ้างหัวข้อในแผน), เกณฑ์ย้ายสถานะ (เมื่อไหร่ย้ายได้ และสถานะไหนใช้กับกรณีไหน ตามกติกาของโปรเจกต์นั้น) และหลักฐานที่ต้องแนบในใบทุกครั้งที่ย้ายสถานะ

### 9. References

อยู่ท้ายสุดเสมอ รายละเอียดเทคนิคทั้งหมดของแผนอยู่ที่นี่ที่เดียว

- วันที่ตรวจ
- repo, branch และ commit ที่ใช้เทียบ
- วิธีตรวจ และความหมายของคำว่า "แก้แล้ว" ในแผนนี้
- สิ่งที่ยังไม่ได้ตรวจ
- ลิงก์ไปแผนหรือเอกสารต้นทาง

## 4. ตารางใบ: 3 ช่องเสมอ

ทุกครั้งที่แผนพูดถึงใบ ใช้ตารางนี้ ไม่ใช้ bullet และไม่เพิ่มช่อง

| รหัส | สรุปเนื้อหา | สถานะบน Plane |
|---|---|---|
| PROJ-123 | ประโยคเดียว ภาษาคน อ่านแล้วรู้เรื่องโดยไม่ต้องเปิดใบ | Todo |

- **รหัส** เป็นรหัสใบเต็ม เช่น `PROJ-123` ไม่ใช้ `#123`
- **สรุปเนื้อหา** ประโยคเดียว ไม่ลอกชื่อใบ ไม่มีชื่อไฟล์หรือชื่อฟังก์ชัน
- **สถานะบน Plane** เป็นสถานะจริง ณ วันที่ตรวจ ตามชื่อที่ Plane แสดง ไม่ใช่สถานะที่คิดว่าควรเป็น

ถ้าอยากใส่ข้อมูลเพิ่ม (เจ้าของ กำหนดส่ง ไฟล์ที่แก้) ให้เขียนเป็นประโยคใต้ตาราง หรือใส่ในหัวข้อ References ไม่ขยายตาราง

## 5. นำขึ้น Plane

1. เขียนเป็นไฟล์ markdown แล้วรัน `check.sh` ของ skill `page` ให้ผ่าน
2. บนสุดของ page มีบรรทัดที่มา ผู้เขียน วันที่ และสถานะ ตามโครงของ skill `page`
3. นำขึ้นเป็น **page ใหม่** ถ้ามีแผนเดิมอยู่แล้ว ห้ามเขียนทับ ให้ลิงก์กลับไปหาแผนเดิมในหัวข้อ References
4. หลังนำขึ้น ตรวจว่าจำนวนตารางและจำนวนแถวใน page ตรงกับไฟล์ แล้วบอกผู้ใช้ให้เปิดดูหนึ่งครั้ง
5. ถ้าเครื่องที่รันเข้า Plane ไม่ได้ ให้ส่งไฟล์ markdown ให้ผู้ใช้วางเอง
